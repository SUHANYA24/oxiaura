# PlantVest AI — Backend Build Specification

> **Purpose of this document:** This is a complete, phase-by-phase build brief for the Flask backend of the *AI-Driven Smart Agreement & Employee Management System with Intelligent Document Verification and Fraud Detection for Plantation Investment Businesses*. Hand this file to Claude Code and build one phase at a time. Do not skip ahead — each phase depends on the one before it. After each phase, run it, confirm it works, then move on.

---

## 0. Project Overview

**What we are building:** A REST API backend for a plantation investment company that automates customer onboarding, employee management, agreement generation, and AI-based document fraud detection.

**Stack:**
- **Language:** Python 3.11+
- **Framework:** Flask (application factory pattern, Blueprints)
- **ORM:** SQLAlchemy via Flask-SQLAlchemy
- **Migrations:** Flask-Migrate (Alembic)
- **Auth:** Flask-JWT-Extended (access + refresh tokens, role-based)
- **Serialization/Validation:** Marshmallow (flask-marshmallow)
- **Async jobs:** Celery + Redis
- **AI:** EasyOCR + OpenCV (document OCR), PyTorch ResNet-18 + Siamese network (fraud)
- **PDF:** Jinja2 + WeasyPrint
- **Database:** MySQL 8
- **Server:** Gunicorn (production), Flask dev server (development)

**User roles:** `admin`, `head_office_staff`, `sales_rep`

## 3. Security Design (applies to every phase)

Bake these in from the start, not at the end:

1. **Passwords:** hash with bcrypt (cost factor 12). Never store or log plaintext.
2. **JWT:** access token 15 min, refresh token 7 days. Include `role` and `user_id` in claims. Maintain a token blocklist for logout/revocation.
3. **Role enforcement:** a `@role_required([...])` decorator that reads the JWT identity and rejects unauthorized roles with 403.
4. **Input validation:** every request body passes through a Marshmallow schema before touching a service. Reject unknown fields.
5. **File uploads:** validate MIME type server-side (not just extension), enforce a max size (e.g. 10 MB), store with a `uuid4` filename in a non-web-served directory, and compute + store a SHA-256 hash on upload. Re-hash on access to detect tampering.
6. **SQL safety:** use the ORM exclusively. No raw string-built queries.
7. **Transport:** HTTPS only in production, CORS restricted to the frontend origin, rate limiting on auth and upload endpoints (Flask-Limiter).
8. **QR tokens:** HMAC-signed with a server secret so agreement authenticity can be verified through a public read-only endpoint.
9. **Audit trail:** log every state change (verification, fraud flag, agreement status) with user id, timestamp, and action.
10. **Secrets:** all secrets in `.env`, loaded via `python-dotenv`. Commit only `.env.example`.

## 4. API Endpoint Map (target)

All under `/api/v1/`.

**Auth**
- `POST /auth/login` — email + password → access + refresh tokens
- `POST /auth/refresh` — refresh → new access token
- `POST /auth/logout` — revoke token
- `GET  /auth/me` — current user profile

**Users** (operator account administration)
- `GET  /users` — list (paginated, filter by role/branch/is_active/search) — management
- `POST /users` — create an operator account (admin only)
- `GET  /users/{id}` — detail + branch — management
- `PUT  /users/{id}` — update profile, role, branch, activation (admin only)
- `DELETE /users/{id}` — deactivate, i.e. clear `is_active` (admin only)
- `POST /users/{id}/reset-password` — admin sets another user's password
- `PUT  /users/me/password` — change your own password (any role)

Users are never hard-deleted: five tables reference `users.id`, so `DELETE` clears
`is_active`, which is also what blocks login. Two guards protect the admin role — a
caller cannot change their own role or activation, and the last active admin cannot
be demoted or deactivated.

**Customers**
- `GET  /customers` — list (paginated, filter by status/rep/search)
- `POST /customers` — register new
- `GET  /customers/{id}` — detail + documents + proposals
- `PUT  /customers/{id}` — update
- `DELETE /customers/{id}` — soft delete (admin only)

**Documents / OCR / Fraud**
- `POST /documents/upload` — multipart upload → queues OCR + fraud job → returns job id
- `GET  /documents/{id}` — metadata + status
- `GET  /documents/{id}/ocr-result` — extracted fields + confidence
- `GET  /documents/{id}/fraud-report` — ela/cnn/siamese + aggregate + verdict
- `POST /documents/{id}/verify` — admin approve/reject

**Agreements**
- `POST /agreements/generate` — create + PDF + QR token
- `GET  /agreements` — list
- `GET  /agreements/{id}` — detail
- `GET  /agreements/{id}/pdf` — download PDF
- `GET  /verify/{qr_token}` — **public** authenticity check

**Products** (admin-managed investment catalog)
- `GET  /products` — list (paginated, filter by category/is_active/search) — any role
- `POST /products` — create (admin only)
- `GET  /products/{id}` — detail + proposal_count — any role
- `PUT  /products/{id}` — update, incl. the `is_active` off-sale toggle (admin only)
- `DELETE /products/{id}` — soft delete, i.e. set `is_deleted` (admin only)

Reads are open to every role because a sales rep has to pick a product when
submitting a proposal; every write is admin-only. Products are never hard-deleted
since proposals reference them. A duplicate name (case-insensitive, among live
rows) returns 409.

**Proposals**
- `POST /proposals` — submit; `product_id` is required and must reference a live, on-sale product
- `GET  /proposals` — list by status
- `PUT  /proposals/{id}` — revise product / amount / notes, only while `submitted` or `rep_review`
- `PUT  /proposals/{id}/advance` — move workflow stage

**Employees / Reports**
- `POST /employees/{id}/targets` — set monthly KPI
- `GET  /employees` — list with KPI
- `GET  /reports/dashboard` — aggregate stats
- `GET  /reports/export` — CSV/Excel with filters

## 5. Phase-by-Phase Build Plan

> Tell Claude Code to complete **one phase per session**. At the end of each phase, verify the acceptance check before continuing.

### Phase 1 — Project skeleton & configuration
**Goal:** a runnable empty Flask app.
**Build:**
- `requirements.txt` with all dependencies.
- `app/extensions.py` instantiating `db`, `migrate`, `jwt`, `ma`, `cors` (uninitialized).
- `app/config.py` with `BaseConfig`, `DevConfig`, `ProdConfig`, `TestConfig` reading from env.
- `app/__init__.py` with `create_app(config)` factory that initializes extensions and a `/api/v1/health` route returning `{"status": "ok"}`.
- `wsgi.py`, `.env.example`, `.gitignore`.
**Acceptance check:** `flask run` starts; `GET /api/v1/health` returns 200.

### Phase 2 — Database models & migrations
**Goal:** all nine tables created in MySQL.
**Build:**
- All models from Section 2 with relationships and enums.
- Wire Flask-Migrate.
- Run `flask db init`, `flask db migrate`, `flask db upgrade`.
- A `seed.py` script inserting one admin user, two branches, and a few sample customers.
**Acceptance check:** tables exist in MySQL; seed runs without error; admin user present.

### Phase 3 — Authentication & role system
**Goal:** working login with role-protected routes.
**Build:**
- `utils/security.py`: bcrypt hash/verify helpers, `role_required` decorator.
- `services/auth_service.py`: authenticate, issue tokens, refresh, logout (blocklist).
- `routes/auth.py`: login, refresh, logout, me.
- `schemas/user_schema.py`.
- JWT config in the factory (expiry, blocklist callback).
**Acceptance check:** login returns tokens; a protected test route rejects missing/invalid tokens (401) and wrong roles (403).

### Phase 4 — Customer module (first full vertical slice)
**Goal:** prove the route → schema → service → model → response flow end to end.
**Build:**
- `schemas/customer_schema.py` (create, update, response variants).
- `services/customer_service.py`: create (with NIC dedup check + auto customer_code), list with pagination/filter, get detail, update, soft delete.
- `routes/customers.py` with role guards (sales_rep can create/list own; admin/staff full access).
**Acceptance check:** full CRUD works via Postman; duplicate NIC is rejected; pagination and filters work.

### Phase 5 — File upload & OCR service
**Goal:** upload a document and extract fields.
**Build:**
- `utils/file_handler.py`: MIME + size validation, UUID storage, SHA-256 hashing.
- `ai/ocr/preprocessor.py`: OpenCV deskew, grayscale, denoise, adaptive threshold, resize.
- `ai/ocr/extractor.py`: EasyOCR run + field parsing (NIC number, name, address, account no, amount, date) with per-field confidence.
- `services/ocr_service.py`: orchestrate preprocess → extract → persist to `documents.extracted_fields`.
- `routes/documents.py`: upload endpoint, ocr-result endpoint.
**Acceptance check:** uploading a sample bank slip returns extracted fields with confidence scores; file stored with UUID name; hash saved.

### Phase 6 — Fraud detection pipeline
**Goal:** three-stage fraud scoring on uploaded documents.
**Build:**
- `ai/fraud/ela_detector.py`: Error Level Analysis + EXIF metadata check → score 0–100.
- `ai/fraud/cnn_classifier.py`: load ResNet-18 weights, return tamper probability 0–1.
- `ai/fraud/siamese_detector.py`: embed image, compare against stored embeddings, return highest similarity.
- `services/fraud_service.py`: run all three, compute weighted aggregate (e.g. 0.3·ELA + 0.4·CNN·100 + 0.3·Siamese·100), set `is_flagged` if > 60, write `fraud_logs`.
- `routes/documents.py`: fraud-report endpoint, admin verify endpoint.
> If trained models are not ready, stub the CNN/Siamese to return deterministic mock scores so the pipeline and API can be tested. Swap in real weights in Phase 6b.
**Acceptance check:** fraud-report returns all three sub-scores + aggregate + verdict; flagged documents create a notification.

### Phase 7 — Async processing with Celery
**Goal:** move OCR + fraud off the request thread.
**Build:**
- `celery_worker.py` and Celery config in the factory (Redis broker).
- `tasks/celery_tasks.py`: a task that runs OCR then fraud for a given document id.
- Change the upload route to enqueue the task and return a job id immediately.
- Optional: a job-status endpoint.
**Acceptance check:** upload returns instantly; worker processes the job; results appear when polled.

### Phase 8 — Agreement generation, PDF & QR
**Goal:** generate a downloadable, verifiable agreement.
**Build:**
- `utils/qr_generator.py`: HMAC-signed token creation + verification.
- `templates/agreement_template.html`: Jinja2 letterhead layout.
- `services/agreement_service.py`: fill template → WeasyPrint PDF → generate QR → store paths + token → sequence agreement_number.
- `routes/agreements.py`: generate, list, detail, pdf download, and **public** `/verify/{token}`.
**Acceptance check:** generating an agreement produces a PDF with an embedded QR; scanning/hitting the verify endpoint confirms authenticity; tampered token fails.

### Phase 9 — Proposals workflow
**Goal:** multi-stage proposal approval.
**Build:**
- `schemas` + `services` + `routes/proposals.py`.
- Workflow state machine: submitted → rep_review → ho_review → approved/rejected, with role checks on each transition.
- Notification on each stage change.
**Acceptance check:** a proposal advances stage by stage; only the correct role can advance each stage.

### Phase 10 — Employee KPIs & reporting
**Goal:** performance tracking and dashboard data.
**Build:**
- `routes/employees.py`: set/get monthly targets, list employees with computed KPI %.
- `routes/reports.py`: dashboard aggregate (customer counts, agreement totals, fraud stats, revenue by branch), and CSV/Excel export with date/branch/rep filters.
- Auto-increment `actual_customers`/`actual_revenue` when relevant events occur.
**Acceptance check:** dashboard returns correct aggregates; export downloads a valid file.

### Phase 11 — Security hardening & tests
**Goal:** production readiness.
**Build:**
- Flask-Limiter on auth + upload.
- CORS locked to frontend origin.
- Global error handlers returning consistent JSON error shapes.
- Audit logging on state changes.
- `pytest` suite covering auth, customer CRUD, upload, fraud scoring, agreement verify.
- A Postman collection.
**Acceptance check:** tests pass; rate limits trigger; unauthorized access is consistently blocked.

### Phase 12 — Deployment packaging
**Goal:** one-command run.
**Build:**
- `Dockerfile` (Gunicorn), `docker-compose.yml` (api + mysql + redis + celery worker).
- Production config wired to env vars.
- README with run instructions.
**Acceptance check:** `docker-compose up` brings the whole stack online; health check passes.

### Phase 13 — Product catalog & proposal linkage
**Goal:** replace the free-text `proposals.product_type` with a real, admin-managed catalog.

**Why:** nothing constrained `product_type`, nothing listed the available products, and
two reps could spell the same product three different ways — so "which product sold"
was not answerable from the data.

**Build:**
- `products` table + model (§2), enum category, `is_active` off-sale toggle and `is_deleted` soft delete.
- Full vertical slice mirroring the customer module: `app/models/product.py`, `app/schemas/product_schema.py`, `app/services/product_service.py`, `app/routes/products.py`.
- Reads open to all roles, every write `admin`-only via `role_required([UserRole.admin])`.
- Auto `PRD-1001`-style codes; case-insensitive name uniqueness among live rows → 409.
- `proposals.product_id` FK (nullable in DB for pre-catalog rows, required by the create schema). `product_type` becomes a server-set snapshot of the product name.
- `PUT /proposals/{id}` to revise product / amount / notes, allowed only in `submitted` and `rep_review`.
- Seed a starter catalog of three products in `seed.py`.

**Acceptance check:** an admin can create a product and a `sales_rep` gets 200 on
`GET /products` but 403 on `POST /products`; a proposal cannot be submitted without a
valid, on-sale `product_id`; renaming a product leaves the `product_type` of an
already-submitted proposal unchanged while its nested `product` reflects the new name.
